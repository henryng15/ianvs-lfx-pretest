Reviewed at head `900ae72` against `37a9c60`. The direction is right — a
`protobuf<=3.20.3` ceiling in an Example does conflict with the `onnx` that core Ianvs
installs. Two points before merge.

**1. The added comment states a constraint the change does not encode.**

```text
# Note: must stay compatible with onnx (installed by core ianvs), which requires
# protobuf>=4.25.1.
protobuf
```

The requirement line is now completely unconstrained, so a resolver may still select
protobuf 3.x — the situation this PR exists to prevent. If `>=4.25.1` is the correct
floor, it belongs in the requirement rather than in a comment above it:

```text
protobuf>=4.25.1
```

That is a one-line change and it makes the PR self-enforcing.

**2. The floor is derived from an unpinned dependency.** Root `requirements.txt:7` lists
`onnx` with no version specifier at all, so which protobuf version onnx actually demands
is itself free to move. Documenting a floor read off today's onnx is fragile. Either
constrain `onnx` too, or phrase the comment as "onnx currently requires >= 4.25.1 as of
<version>" so a future reader knows it needs rechecking.

**Confirmed correct:** removing the `# Or use the provided run_ianvs.sh script` line is
right — no `run_ianvs.sh` exists anywhere under `examples/industrialEI/`.

For context on why the encoded-vs-documented distinction matters here: across all Example
requirements files in the repository, 302 of 536 requirement lines carry no version
constraint at all. Comments describing intended bounds are common; enforced bounds are
not.

**Recommendation: minor revision** — change `protobuf` to `protobuf>=4.25.1`.
